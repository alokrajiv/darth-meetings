⏺ The map's complete — I have everything I need. The design:

  - Import button unblocks when artifacts are pending: radios render off
  "present or pending", and if the chosen mode's dependency isn't ready yet, the
  server queues it instead of importing.
  - Placeholder row (defer-<uuid>, status waiting) appears in the listing
  immediately — same precedent as the up-<uuid> uploading rows — carrying a
  deferredImport marker in gmeet_context with the frozen options (mode,
  docId/fileId if known, event, recordName).
  - Dependency logic: transcript mode waits for the transcript Doc only; video
  waits for the video file only; both waits for both (Doc-parse failures are
  swallowed in 'both', so firing early would silently lose the Meet transcript).
  - New 60s poller (recording-poller pattern, owner's server token) re-lists
  artifacts, and when the dependency lands, runs the real import server-side;
  video-mode promotes the placeholder in place via the existing
  promoteUploadingRow hook, 24h give-up flips it to error.

  the poller can run it without a browser session. Let me read the route.

⏺ Here's the full picture, with the EXPLAINs.

  What the endpoint actually does — for a normal call, exactly one SQL query,
  then JSON. No external API calls: the AssemblyAI refresh fan-out only fires
  for rows in queued/processing status (usually zero;
  completed/error/placeholder rows never touch AAI). Auth is an in-process RS256
  JWT verify (~1ms). So the whole cost was the query.

  Where the 200ms went — yes, I ran EXPLAIN (ANALYZE, BUFFERS) on prod data. The
  query was 194ms, and ~192ms of that was one thing: the suspected-series "…?" 
  chip. For every visible row without a series (184 of your 270), a LATERAL join
  scanned all 60 series_keys, and the match predicates run normalization
  regexes (strip date tokens from titles, strip _R20260217T… suffixes from
  recurring IDs, etc.) — evaluated per row × key pair. That's ~11,000 regex
  executions per listing call. The plan showed it plainly: Seq Scan on 
  series_keys … 0.97ms × 184 loops ≈ 178ms. Pure CPU, not I/O.

  Do we need indexes? No. The tables are tiny — 270 transcripts, 60 keys, 604
  shares — every scan completes in microseconds (Seq Scan on transcripts: 0.26ms
  total). An index can't help regex CPU anyway, and the OR-across-six-key-kinds
  shape wouldn't use one. Indexes become worth revisiting around thousands of
  rows, not now.

  The fix (deployed last night): the regexes only depend on the row, not the key
  — so I hoisted them into a CTE evaluated once per row. One catch: a plain
  subquery gets inlined by the planner and you're back to per-pair evaluation (I
  measured it — 178ms, barely better). WITH norm AS MATERIALIZED forces the
  fence. Current plan confirms it: CTE norm → 1 row per loop, keys scan now
  0.004ms.

  Numbers:

  │                         │ before │  after  │
  ├─────────────────────────┼────────┼─────────┤

  ├─────────────────────────┼────────┼─────────┤
  │ endpoint, on the VM     │ ~195ms │ 46–54ms │
  └─────────────────────────┴────────┴─────────┘

⏺ No — it's not paginated. GET /api/transcripts returns every row you can see in
  one shot: currently 270 rows ≈ 280KB of JSON. And that's a deliberate design,
  not an accident: the tabs (All/Mine/Shared/Trash), search-as-you-type, day
  grouping, column sorting, and the SSE live-reload all operate on the full
  array in the browser. Paginating just the API would break all of that — you'd
  have to move search, tabs, and grouping server-side in the same change.

  Is full-list wrong at this scale? No. At 270 rows / ~50ms query / 280KB it's
  the simplest correct design. But while checking I found the actual
  embarrassing gap:

  The response isn't gzipped. I sent Accept-Encoding: gzip and got all 279,664
  bytes back as identity — nginx isn't compressing JSON on this vhost. Listing
  JSON like this compresses ~6–8×, so that's 280KB → ~40KB over your VPN, for a
  one-line nginx config change. That's the biggest remaining perceived-speed
  win, bigger than anything left in SQL.

  When does full-list actually break? Growth is accelerating — 116 rows in
  August alone (multi-user + auto-share), vs ~20-40/month before. Call it 1.5–3k
  rows within a year. Two things degrade, at different points:

  1. ~1k rows without a series: the suspected-series chip cost is O(unattached
  rows) — the 33ms creeps back toward 180ms. Fix at that point: stamp the
  normalized key values on the row at write time, so the chip becomes a plain
  equality join. That keeps full-list viable well past this.
  2. ~2–3k rows: the payload itself (2-3MB raw, ~300-400KB gzipped) starts
  hurting first paint. That's when real pagination earns its complexity — as a
  bundle: cursor pagination by day (fits the day-grouped view naturally — load
  newest N days, infinite-scroll older), server-side tab filters, and search
  fully server-side (the deep-search endpoint already exists for that). Plus
  ETag/304 on the SSE-triggered refetches, since most of them return identical
  data.

  row count actually demands it, and as the full bundle. Want me to do the gzip
  one?
