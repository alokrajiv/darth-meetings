⏺ Here's the angle — I've verified the key facts rather than guessing.

  Why you're stuck on Retry

  - trames-auth-session JWT lives 24h (kenoby-sso/src/lib/jwt.ts:56), but the
    cookie itself has a 30-day maxAge on .trames.io. So after 24h the cookie is
    still present but expired.
  - Our src/proxy.ts only checks cookie presence (Edge can't verify RS256), so
    the page loads fine; then every /api/* call hits withAuth → real verify
    → 401.
  - Nothing on our side ever calls refresh, so Retry just re-fails. /login would
    work but only via a full bounce to login.trames.io/dashboard.

  How the other two apps do it

  - login.trames.io: /api/auth/refresh — reads trames-auth-session (decode-only,
    expiry ignored) + cognito_refresh_token (30d, .trames.io, httpOnly),
    rotates with Cognito, re-sets both cookies on .trames.io. Supports
    ?returnTo= redirect mode or Accept: application/json mode.
  - kyloren (app.trames.io): it's not actually a popup for refresh —
    src/services/ssoAxios.ts is an axios response interceptor: on
    401/SESSION_EXPIRED → single-flight POST 
    https://login.trames.io/api/auth/refresh with withCredentials → replay the
    original request once. The window.alert(...) in App.tsx is the separate
    jti-changed/org-switch case.

  Can we do the same from meetings.darth-internal.trames.io? Yes — verified

  curl -X OPTIONS -H "Origin: https://meetings.darth-internal.trames.io"
  https://login.trames.io/api/auth/refresh
  → access-control-allow-origin: https://meetings.darth-internal.trames.io
    access-control-allow-credentials: true
  *.trames.io is in kenoby's APPROVED_HOSTS wildcard, both cookies are on
  .trames.io with SameSite=Lax (same-site fetch → sent), and the rotated
  Set-Cookie from login.trames.io lands on .trames.io → our app sees it
  immediately. No CORS or cookie-domain work needed.

  Proposed fix (two halves, small)

  1. Client — global 401 interceptor (~60 lines, one file + mount in
     layout.tsx): we have 118 raw fetch( calls across 28 client files and no
     wrapper, so rather than touching them all, wrap window.fetch once for
     same-origin /api/ calls: on 401 → single-flight
     fetch('https://login.trames.io/api/auth/refresh', {method:'POST', 
     credentials:'include', headers:{Accept:'application/json'}}) → replay once.
     If refresh 401s (refresh token dead / jar wiped) → location.href = 
     '/login?returnTo=…'. Skip retry when the caller is /api/auth/* or the
     request is a non-replayable body stream (the multi-GB upload route).
  2. Server — proxy.ts exp pre-check for page loads: base64-decode the JWT
     payload (no verify, fine on Edge), and if exp < now redirect navigations to
     https://login.trames.io/api/auth/refresh?returnTo=<current URL> — the
     route already whitelists *.trames.io returnTo. Result: opening a tab after
     24h silently rotates and lands back on the page, no 401 flash at all. API
     calls keep returning 401 (the client half handles those).

  Caveats worth knowing: refresh is allowlisted to
  @trames.sg/@trames-engineering.com emails (everyone here), and a failed
  refresh wipes the jar (Max-Age=0) — that's acceptable in a browser (→
  re-login), just the thing that bites the curl jar.

  Want me to build both halves now? It's ~1 hr including a Playwright check with
  a deliberately expired JWT on prod.

  Kyloren after SSO — how it "manages without anything"

  It doesn't hold Cognito tokens itself anymore; it delegates the Cognito 
  refresh to kenoby-sso and just pokes it. Two layers in current prod-v3:

  1. src/services/ssoAxios.ts (axios instance with baseURL = 
     https://login.trames.io, withCredentials: true) — response interceptor: on
     401 / SESSION_EXPIRED → single-flight POST /api/auth/refresh (Accept: json)
     → replay the original call once. This is a cross-origin call from 
     app.trames.io → login.trames.io, exactly our situation.
  2. src/services/httpHook.ts (the travis API axios) — on 401 →
     refreshSessionSilently() → doInitialSSOSetup() → which goes through
     ssoAxios.get('/api/auth/session') → the interceptor above fires the refresh
     → then replays the travis request. Plus App.tsx re-checks the session on
     window focus via getSSOUserWithError(), which also passes through the same
     interceptor.

  So the "Cognito refresh token" still exists — it's the encrypted
  cognito_refresh_token cookie kenoby-sso sets on .trames.io (30d, httpOnly).
  Kyloren never sees it; the browser just carries it to login.trames.io when
  kyloren hits /api/auth/refresh. No popup for this path — the window.alert in
  App.tsx is the separate "your org/group/user changed (jti mismatch), reload"
  case.

  Am I confident the cross-domain refresh works? Yes — now proven with real 
  cookies, not just preflight

  Why that translates to the browser:
  - Both cookies are Domain=.trames.io; SameSite=Lax.
    meetings.darth-internal.trames.io → login.trames.io is same-site (same
    eTLD+1), so a fetch(..., {credentials:'include'}) sends them.
  - CORS echoes our exact origin + allow-credentials: true, so the browser
    accepts the response and applies its Set-Cookie — the new JWT lands on
    .trames.io and our app reads it on the next request.
  - Cognito did not rotate the refresh token in that call (no new
    cognito_refresh_token Set-Cookie), so my curl didn't disturb your browser's
    copy.
  - Kyloren does literally this cross-origin in prod every day — we'd be the
    second consumer of an already-working path, not a new one.
