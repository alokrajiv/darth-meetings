⏺ Yes — she is, and I've traced exactly why. Here's the full picture:

  What Jac is seeing

  The "Not imported" view reads the global gmeet_meeting_cache — the org-wide
  artifact cache that every connected user's poller writes into — with no check 
  that the caller's own calendar contains the meeting. unimportedWhere() in
  src/db-ops/calendar-event-cache.ts:412 filters only on "has artifacts" +
  "nobody imported it" + mutes/dates. So any signed-in user sees every
  unimported meeting from everyone's calendars: titles (pulled from any user's
  gmeet_reminders row — the code comment even says "Any user's row works"),
  organizer emails, times, durations, recording/transcript badges, and the new
  Teams "held/recorded" chat verdicts. That's how Jac gets "alok <> swaralee -
  lp" and everyone else's scrums on her screen.

  Not a regression — and what changed to make it blow up now

  - I diffed last night's perf commit (a670605) against the original: it
    preserved semantics exactly. And the original unimportedWhere from listing
    v2 (7bf6943, Aug 19) never had caller scoping either. The norec view is
    strictly per-user; the unimported view was global from day one.
  - What made it suddenly glaring: the Teams chat call-events work (e71f7a8,
    yesterday) plus its 60-day chat backfill doubled the cache, and Friday's UX
    commit put the layers dropdown front and center. The exposure existed for 5
    days; the volume and visibility landed this weekend.

  Severity boundary

  Content is not leaking: I checked executeGmeetImport — the Import button uses
  the clicker's own Google token (browser token, or their own server-minted one
  on the deferred path), so Google's Drive/Docs ACLs gate the actual
  transcript/recording. If Jac clicks Import on Alok's 1:1 she gets a Google
  permission failure. What leaks is metadata — which, for titles like private
  1:1s, is still a real privacy problem.

  The fix I'd make

  Scope unimportedWhere to occurrences the caller can evidence involvement in:
  require an EXISTS against their own calendar_event_cache rows matching
  (meeting_code, ±12h) — the exact join the cal display-lateral already does,
  just promoted from optional enrichment to a hard predicate (falling back to an
  attendee-email match on the cached attendees jsonb if you want
  invitee-but-different-calendar coverage). Since the counts, day-bucket, and
  rows queries all share unimportedWhere, one change fixes the tab count, the
  listing, and pagination together. One edge to handle: Teams chat-derived rows
  (teams-… codes) — those need to stay visible to the user whose chat sweep
  produced them.

  Say the word and I'll implement + deploy it now.

⏺ Yes — your instinct is right: that exact failure mode exists in the code. I've
  confirmed the mechanism, and it's three stacked issues in
  src/app/transcript/[id]/page.tsx:

  Why stale state is possible when you navigate A → B:

  1. The page component never remounts between transcripts. Navigating
     /transcript/A → /transcript/B is the same route segment in the Next.js app
     router, so the component instance survives with all ~30 pieces of state —
     row keeps holding A's data (title, speakers, audio src) until the fetch for
     B resolves. If B is mid-import, that window is when you're looking at B's
     URL with A's player still loaded and playing.
  2. The audio player is keyed by video-part only, not transcript
     (key={activePart} at page.tsx:2571) — so on nav the same <audio> element is
     reused and just has its src swapped whenever the row finally updates.
  3. The real kicker — a stale-reload race with no guard: live collaborator
     events schedule a debounced loadAll({silent:true}) on a 1-second timer
     (page.tsx:491). That timer is never cancelled when the transcript id
     changes, and loadAll has no "is this response still for the current id"
     check. So: an event for A arrives, you click through to B, one second later
     the old timer fires the old loadAll closure and writes A's row back into 
     state on B's page. Since B is still importing, nothing corrects it until B
     emits its own event or you refresh. Play a speaker sample in that state and
     you hear A's audio under B's URL.

  So both things you observed yesterday were real but different: the Mandy voice
  is genuinely in the 1:1 recording (played-back LP-Global audio — I matched
  Speaker A's words to the LP-Global calls' "Helsinki/TAOT/name account"
  content), and this stale-navigation bug can independently show you the wrong
  meeting's page state, which is probably what made it feel like a totally
  different meeting.

  The fix is small and surgical: wrap the page body in an inner component
  rendered with key={transcriptId} — that force-remounts on every transcript
  change (all state resets, player unmounts, audio stops instantly), and it
  neuters the stale-timer race because the old instance's setRow becomes a
  no-op. Plus a one-line stale-response guard in loadAll for good hygiene. Want
  me to ship it?
